# /plan - 기획

기능 요청을 **화면(씬) · 서버 API · 데이터 모델** 세 축으로 나누어 구현 순서를 정한다.

## 프로젝트 컨텍스트

> - **CLAUDE.md**: 메모리 예산 · 금지 사항 · 서버 우선 계산 원칙
> - **README.md**: 씬 목록 · API 목록 · 데이터 모델 (단일 출처)
> - **기획서**: CLAUDE.md의 Confluence 링크. 12개 씬과 성장 규칙의 원본
> 위 소스와 어긋나는 요청이면 어느 쪽을 바꿀지 먼저 묻는다.

## 역할 원칙

- 1인 개발이다. 스토리·수용 기준 같은 팀 의식은 생략한다. **무엇을 · 어디를 · 순서**만.
- "지금 만들 이유가 있나"를 먼저 묻는다. 기획서에 있어도 1.0 범위가 아니면 미룬다.
- 성장·랭킹·일일 제한 같은 규칙은 **서버 계산**으로 설계한다. 클라이언트는 표시.
- 메모리 예산(CLAUDE.md)을 넘는 설계는 만들지 않는다.

## 워크플로우

### Phase 1: 요구 정리
1. 요청을 "어느 씬에서 무엇을 하면 무엇이 된다" 한두 줄로 옮긴다.
2. 기획서·README와 대조해 이미 정해진 규칙(수치·제한)이 있으면 그대로 쓴다. 없으면 기본값을 제안하고 확인받는다.

### Phase 2: 세 축으로 분해
| 축 | 적을 것 |
|---|---|
| 씬 | 새 씬인지 기존 씬 수정인지. 필요한 에셋(텍스처·오디오)과 예상 크기 |
| 서버 API | 엔드포인트 · 요청/응답 필드 · 어떤 테이블을 읽고 쓰는지 |
| 데이터 모델 | 새 테이블/컬럼 · UNIQUE 제약으로 해결되는 규칙 |

### Phase 3: 순서
서버 → 클라 순서가 기본이다 (서버 없이 클라를 만들면 두 번 만든다).
```
## 실행 계획
1. [S] 서버: 테이블 + 엔드포인트
2. [M] 클라: 씬 · UI · API 호출
3. [S] 검증: Memory Profiler 스냅샷 · 빌드 크기
### 미루는 것
- 기능 X (이유)
```
복잡도: `[S]` 반나절 이하 / `[M]` 하루 / `[L]` 며칠. `[L]`이 나오면 쪼갠다.

### Phase 4: 기록
확정되면 README.md의 로드맵/API/데이터 모델 절을 갱신한다. 대화에만 남기지 않는다.

## 완료 상태
- **DONE**: 세 축과 순서가 정해짐, `/build` 가능
- **DONE_WITH_CONCERNS**: 확인 못 한 수치·규칙이 남음 (목록)
- **NEEDS_CONTEXT**: 기획서에도 없고 사용자 결정이 필요한 규칙이 있음

## 안전장치
- 새 씬이 메모리 예산표(텍스처 합 48MB · 다운로드 15MB)를 넘길 것 같으면 계획 단계에서 경고
- 클라이언트에서 규칙을 계산하는 설계가 나오면 서버로 옮기라고 지적
- 1.0 범위(홈→안내→로그인→알→캐릭터→홈화면) 밖 기능을 1.0에 넣으려 하면 확인
